# T08 패스키 인증 구현 설명서

## ① 무엇으로 붙였나

WebAuthn 패스키를 `@simplewebauthn/server` 13.2.2로 검증합니다. 서버는 등록·로그인마다 무작위 challenge를 발급해 D1 `challenges`에 5분간 보관합니다. 등록 결과에서는 credential ID, 공개키, 카운터, 전송 수단만 `credentials`에 저장합니다. 로그인 성공 후에는 서버 DB 세션과 `HttpOnly; Secure; SameSite=Strict` 쿠키를 사용하며 7일 뒤 만료합니다. 개인키와 비밀번호는 서버에 저장하지 않습니다.

## ② 왜 골랐나

WebAuthn의 원본 주소·RP ID·서명·challenge·카운터 검사를 검증된 라이브러리에 맡기기 위해 선택했습니다. 직접 서명 검증 알고리즘을 작성하는 방법도 검토했으나 검증 누락 위험이 커서 고르지 않았습니다. 공개 소개 내용은 인증 없이 열리고, 가상 메모 세 건은 인증 뒤 API에서만 내려줍니다.

## ③ 어디를 어떻게 고쳤나

| 흐름 | 화면 | 서버 |
| --- | --- | --- |
| 등록 | `passkey.js`의 `navigator.credentials.create` | `worker/index.js`의 `/api/register/options`, `/api/register/verify` |
| 로그인 | `passkey.js`의 `navigator.credentials.get` | `worker/index.js`의 `/api/login/options`, `/api/login/verify` |
| 로그아웃 | `passkey.js`의 로그아웃 버튼 | `worker/index.js`의 `/api/logout`: 서버 세션 삭제 |
| 비공개 자료 | `passkey.js`의 로그인 후 목록 | `worker/index.js`의 `/api/private`: 세션 계정 ID로만 조회 |
| 패스키 관리 | 이름·등록 날짜·삭제 버튼 | `worker/index.js`의 `/api/passkeys`와 `/api/passkeys/delete` |

T01 원본의 공개 HTML·CSS·사진은 유지했습니다. 새 비공개 자료는 HTML 소스에 넣지 않았으며 서버 DB에 가상 문구로 저장합니다.

## ④ 안 열리는 것을 확인한 기록

아래는 `tests/browser.mjs`의 **로컬 가상 인증기·임시 DB** 결과입니다. 계정과 키는 시험용이며 쿠키·개인키 원문은 기록하지 않았습니다.

| 확인 | 통과 요청 → 응답 | 거절 요청 → 응답 |
| --- | --- | --- |
| 로그인 없이 열기 | `GET /` → 200, 공개 소개 보임 | `GET /api/private`, 쿠키 없음 → 401 |
| 남의 패스키로 열기 | 계정 B의 패스키로 B 로그인 → 200 | 계정 A의 challenge에 B 패스키 응답 → 403 |
| 질문 재사용 | 새 challenge에 한 번 서명해 로그인 → 200 | 같은 응답을 다시 `POST /api/login/verify` → 403 |
| 패스키 삭제 뒤 로그인 | 두 키 중 첫 키 삭제 뒤 남은 키로 로그인 → 200 | 로그아웃 뒤 같은 세션으로 `GET /api/private` → 401 |

서로 다른 계정의 요청은 `credentials.account_id`와 challenge의 `account_id`를 함께 비교해 거절합니다. 개인 메모는 세션의 `account_id`로 조회합니다. 로컬 검사에서 두 계정의 메모는 각각 3건이며 거절 전후 건수가 유지됐습니다. 실제 기기 두 개 등록과 저장 위치는 공개 앱에서 따로 확인해야 합니다.

## ⑤ AI와 나

- AI에게 맡긴 일: WebAuthn 서버·화면·계정별 자료 격리·가상 인증기 검사를 구현했습니다.
- 내가 직접 판단한 일: T01의 공개 소개를 유지하고 비공개 공간에는 가상 메모 3건을 쓰기로 결정했습니다.
- AI 제안을 따르지 않은 일: 아직 별도로 거절한 구현 제안은 없습니다. 실제 기기 등록 결과를 가상 인증기 결과로 대신 기록하지 않았습니다.

## ⑥ 아직 못 막은 것

- 마지막 패스키는 삭제를 거부합니다. 기기 두 대를 모두 잃으면 계정을 복구하는 별도 절차가 없어 개인 메모에 다시 들어갈 수 없습니다.
- 가입 가능한 아이디에 대한 속도 제한은 아직 없습니다. 자동화된 가입 시도로 저장 공간이 소모될 수 있습니다.

## 실제 기기 확인 상태

로컬 가상 인증기로 두 패스키와 두 계정의 인증 흐름을 확인했습니다. 실제 기기의 패스키 두 개 등록, 저장 위치, 하나 삭제 뒤 남은 키로 로그인한 결과는 사용자 확인 뒤 추가합니다.
